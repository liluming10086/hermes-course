Hermes 实操课

这门课不教你"有哪些功能"，教你遇到任何 Agent，怎么用 5 分钟判断该配什么、配在哪、值不值得配。每章都是"为什么 + 现在动手 + 怎么验证"。

面向：AI 初学者 主线：编程 · 项目管理 · 论文 平台：Windows · 桌面版 12 章 + 3 附录

00你的起点诊断

先看清"你已经有什么"，否则后面每一章你都会误以为要从零开始。

开课前我实际扫了你这台机器（D:\Hermes），结论是：你的问题不是"缺东西"，而是"库存过剩、使用方法为零"。

项目实际状态意味着
技能 Skills16 个分类、上百个技能已装能力天花板很高，但你一个都没主动用过
插件 Pluginsplan-mode、ponytail 已启用；hindsight 被禁用装了"行为模式"类插件，但从未触发过一次
桌面插件目录为空最容易出效果的一块，完全没碰
自己写的 skill0 个Hermes 最核心的"自我进化"机制，等于闲置
memory / USER.md已填：18% / 63%你已经在用它记偏好，方向是对的
AGENTS.md无进任何代码仓库，我都是"空手"进去的
gh CLI未安装github 技能现在调用必然失败
初学者最典型的死循环

花 80% 时间找插件、装插件、看别人推荐；花 0% 时间把一件真实的事交给它做。结果：装了一堆，遇到真问题还是自己干。这门课的全部目的，就是帮你把这个比例倒过来。

类比：把 Agent 想成一个刚入职的高水平实习生。他智商很高（模型），手也会用（工具），但他不知道你公司怎么干活。你现在的状态是——办公室里堆满了专业书（技能），你连他叫什么都没告诉，就抱怨他不好用。

这门课的三条原则

  1. 先最小可用，再谈优化。能一句话解决的，绝不写成一个 skill。
  2. 每配一样东西，必须知道它的"预算成本"。Agent 的上下文窗口是公共资源，所有常驻配置都在抢它。
  3. 配完必须验证。没验证过的配置 = 不存在的配置。

01Agent 到底是什么

不理解这一章，后面所有配置都是背命令。

大模型（LLM）只会做一件事：看一段文字，猜下一个字。它自己不能上网、不能读文件、不能记住上次聊了什么。

Agent 是在外面套了一圈"外骨骼"：

AGENT 的最小循环
你说话
  ↓
[ 系统提示词 ] + [ 历史对话 ] + [ 工具清单 ]   ← 拼成一大段文字
  ↓
模型输出："我要调用 read_file，参数是 xxx"
  ↓
Hermes 真的去读了文件，把结果塞回对话
  ↓
模型再看一遍，继续下一步 …… 直到它说"完成了"
  ↓
把结果给你

关键在第二行：模型的"记忆"和"知识"，本质上就是"这次请求里塞进去的文字"。塞不进去的，它就不存在。

类比：模型是一个每天早上失忆的天才。它能力很强，但昨天的事全忘。所谓"配置 Agent"，就是每天早上给它留一张便签——便签上写什么、写多长，决定了它今天表现如何。

于是所有配置问题，都变成同一个问题

"这段话，是每次都要给它看的，还是用到时才给它看的？"

你的信息性质该放哪
"说话别客套，直接给结论"每次都要SOUL.md
"我用 Windows，主目录是 C:\Users\<用户名>"每次都要、很短memory
"这个仓库用 pnpm，测试命令是 pnpm test"只在这个仓库要AGENTS.md
"怎么把论文 PDF 拆成可检索笔记的完整流程"用到才要、很长SKILL.md
"能连数据库查数的工具"是能力，不是知识插件 / MCP
一句话记住

常驻的东西必须短，长的东西必须按需加载。这就是为什么 Hermes 的文档里反复出现"渐进式披露（progressive disclosure）"这个词——它不是玄学，是省钱的工程手段。

一个具体的数字：指令预算

业界实测（Humanlayer 提出、被广泛引用）：前沿模型在一次请求里能稳定遵循的指令大约只有 150–200 条。超过之后不是报错，而是开始随机忽略其中一些——而且你永远不知道它忽略了哪条。

这条规律直接决定了第 5 章 AGENTS.md 该怎么写。现在只需记住结论：写得多 ≠ 管得住。写太多等于没写。

02五层配置地图

这是全课最重要的一张图。以后你换任何 Agent（Claude Code、Codex、Cursor）都能套用。

五个抽屉

层文件加载时机容量写什么
① 身份SOUL.md每次会话开头，永远加载短语气、风格、绝对禁令
② 事实memory / USER.md每次会话开头，自动注入2200 / 1375 字符关于你和环境的具体事实
③ 项目AGENTS.md在那个目录里干活时指令预算 150–200 条这个仓库怎么构建、测什么、别碰什么
④ 技能SKILL.md按需，靠 description 触发正文 ≤500 行一类任务的完整流程
⑤ 能力插件 / MCP启动时注册成工具—新的"手"，不是新的"知识"
一句话形象类比：SOUL 是性格，memory 是记忆，AGENTS.md 是这家公司的员工手册，SKILL.md 是工具箱里那本"用到才翻"的说明书，插件是给他配的新工具。

决策树：一条信息该放哪

贴墙上的那一张
这条信息，是关于"怎么做事"还是"是什么"？
│
├─ 怎么做事（流程、步骤、命令序列）
│    ├─ 只在一个项目里成立 → AGENTS.md
│    └─ 跨项目都成立，且超过 10 行 → SKILL.md
│
└─ 是什么（事实、偏好、环境）
     ├─ 每次都要知道，且一句话说得清 → memory
     ├─ 是"我要它怎么跟我说话" → SOUL.md
     └─ 只说一次就够，属于这次任务 → 什么都别写，说在对话里
三个最常见的错放

1. 把流程写进 memory。memory 只有 2200 字符，一个部署流程就能吃光，还会挤掉真正的偏好。

2. 把项目规则写进 SOUL.md。SOUL 是全局的，你换个仓库它还在，会污染无关项目。

3. 把"这次任务的临时要求"写成 skill。一次性的东西沉淀成 skill，等于给自己养了个负担——第 10 章会讲怎么清理。

你在 Hermes 里的实际路径

官方文档写的是 ~/.hermes/，但你的是自定义安装位置，实际路径是：

bash
D:\Hermes\
├─ SOUL.md                 ← ① 身份（全局唯一）
├─ config.yaml             ← 设置（模型、终端、压缩…）
├─ .env                    ← 只放密钥，不放设置
├─ memories\               ← ② MEMORY.md / USER.md
├─ skills\                 ← ④ 技能（16 个分类）
├─ plugins\                ← ⑤ 你装的插件
├─ desktop-plugins\        ← 桌面 UI 插件（你这里是空的）
├─ profiles\               ← 多套独立人格（现在没有）
└─ state.db                ← 所有历史会话（可搜索）

bash

03SOUL.md：只写"性格"，不写"知识"

最容易写错的一层。90% 的人把它当成第二个 memory 用。

SOUL.md 在每次会话开头逐字注入，位置在系统提示词的最前面（slot #1）。这意味着两件事：

  • 它永远生效——不需要触发词，不像 skill 那样可能没被选中；
  • 它的每个字永远占预算——写得越长，留给任务的空间越少。

判断标准：3 个问题

问题是 → 写进 SOUL否 → 去哪
它对所有任务都成立吗？✓AGENTS.md / skill
它描述的是怎么说话/怎么决策，不是某个领域的事实？✓memory
删掉它，我会立刻感觉到"这家伙不像我的助手了"？✓说明它其实可有可无

好的 SOUL.md 长什么样

结构就四块，别多：

SOUL.md 模板
## 语气
- 直接给结论，不写"好问题""我很乐意"。
- 不确定就说不确定，不要编。
- 中文回答；代码、命令、路径保持原文。

## 决策方式
- 有多个方案时，给 2–3 个选项，标出推荐项和理由。
- 改动超过 3 个文件，先说方案等我点头，再动手。

## 硬禁令
- 不碰 `D:\公司资料\` 下的任何文件。
- 删文件、改系统配置、花钱的操作，一律先问。
- 不替我做 git push，只提交到本地。
为什么"硬禁令"要单独拎出来

Agent 的安全边界不能靠模型自觉。写进 SOUL 的禁令会在每一轮都被读到，是成本最低的一道保险。当然，真正确凿的护栏是 Hermes 的危险命令审批机制（第 8 章提），SOUL 只是第一层。

1. 先看你现在写了什么

2. 用对话方式改，不要手改文件

直接在聊天里说这句话，我会帮你改并保留原文：

改之前先把现在的内容给我看。

3. 验证生效

开新会话（/new）随便问一句，看语气有没有变。SOUL 是会话级快照，当前会话改了要新会话才生效。

  • 我的 SOUL.md 里没有项目相关的规则（那些属于 AGENTS.md）

04memory：唯一有硬上限的一层

预算只有 2200 + 1375 字符。花法决定它有多大用。

Hermes 的记忆由两个文件组成，都在 memories\ 目录：

文件内容上限典型条数
MEMORY.mdAgent 自己的笔记：环境事实、约定、踩过的坑2200 字符（≈800 tokens）8–15 条
USER.md关于你的画像：偏好、风格、水平1375 字符（≈500 tokens）5–10 条

三个必须知道的机制

  1. 冻结快照。会话开始时读一次，之后整场对话不再变。你这一场里让我记的东西，我当场能看到（工具返回里），但要写到系统提示词里得等下一场。原因：保持前缀缓存，省钱。
  2. 不会自动压缩。写满就报错，不会悄悄丢掉旧的。设计意图是逼你主动整理，而不是让重要信息无声消失。
  3. 条目用 § 分隔，可以多行。你在系统提示里看到的那一坨就是它。
类比：memory 是贴在显示器边上的便利贴，不是笔记本。便利贴只能写"周三交稿""这台机器没装 gh"这种；写不下的，说明它本来就该进笔记本（skill）。

该写 / 不该写

✓ 写进 memory✗ 别写
"这台机器没装 gh，用 git 代替""Python 3.14 支持 f-string 嵌套"（能查到）
"我的项目都在 D:\code 下，用 venv"整段报错日志、代码块
"不要用 sudo，我在管理员组""用户问过 Python"（太模糊）
"论文用 GB/T 7714 引用格式"临时文件路径、一次性调试上下文
"上次迁移数据库是 2026-03-01"SOUL.md / AGENTS.md 里已有的内容（重复占预算）
你现在的位置：USER.md 已用 63%，MEMORY.md 18%

USER.md 比预想的满。通常原因是把"流程"写进了画像——比如"沟通风格"那条里塞了一大段双代理协作协议，那其实更接近一个 skill。而"结项反馈偏好""高代价方案触发规则"这类，属于决策规则，既不像画像也不像流程，是 memory 的合理用法。

判断方法：如果一条记录超过 200 字符，先怀疑它该不该是个 skill。

05AGENTS.md：项目手册，越短越好

这一层的反直觉之处：写得越全，效果越差。

把 AGENTS.md 放进仓库根目录，我进这个目录干活时会自动读到。它是整个行业的事实标准——Claude Code、Codex、Cursor、Copilot、Gemini CLI 都认这个文件。所以这一章学一次，换任何工具都能用。

Hermes 的实际加载规则（比你想象的细）

规则行为
优先级.hermes.md → AGENTS.md → CLAUDE.md → .cursorrules，只取第一个命中的
git 仓库内从仓库根到当前目录，链式合并所有 AGENTS.md，越深越靠后 = 优先级越高
子目录我在会话中途读进某个子目录时，渐进发现那里的 AGENTS.md 并注入（每个目录只查一次）
git 仓库外只看当前目录，不往上找——防止 D:\ 或用户主目录里的文件污染无关会话
安全内容会过一遍提示注入扫描，命中就整份不加载，并显示 [BLOCKED]
体积超限会截断（默认保留头 70% + 尾 20%），中间被丢
这个"链式合并 + 子目录渐进"设计的意义

你可以在 monorepo 里让前端目录写"用 pnpm"，后端目录写"用 poetry"，两条规则互不打架，而且只有我真正读那边文件时才占预算。这就是"渐进式披露"在文件系统层面的落地。

指令预算：为什么必须狠

前面说过 150–200 条的上限。AGENTS.md 的每一行每次请求都加载，跟这次任务相不相关都一样。于是产生一个恶性循环：

文件是怎么烂掉的
Agent 做了一件你不喜欢的事
  → 你加一条规则防止它
  → 下个月又一件
  → ……重复几十次
  → 文件变成"泥球"（ball of mud）
  → 规则互相矛盾，Agent 开始随机遵守
  → 你觉得"这 AI 不太行"
比臃肿更危险的是：过期

文档里写 认证逻辑在 src/auth/handlers.ts，那个文件被改名了。人类看到过时文档会怀疑；Agent 会自信地跑去错误的位置。所以：不要记录文件结构，要描述"能力"和"领域概念"——概念比路径稳定得多。

根目录只留三样东西

该留例子
① 一句话项目描述这是一个无障碍数据可视化的 React 组件库。
② 包管理器（非默认时）本项目用 pnpm workspaces。
③ 非标准的构建/检查命令构建: pnpm build:lib　类型检查: pnpm tsc --noEmit

其余全部走渐进披露——拆成 docs/ 下的文件，或者做成 skill。

看一个"瘦身版"根 AGENTS.md 的完整样子
AGENTS.md

# 环境

06SKILL.md：本课的核心

这是 Hermes"越用越强"的唯一机制。学会这一章，你就掌握了所有 Agent 的通用扩展方式。

Skill 就是一个带 YAML 头的 Markdown 文件，放在 skills\ 下的某个目录里，文件名必须叫 SKILL.md。没有编译、没有注册、没有重启——放进去就生效（新会话生效）。

它是开放标准

Anthropic 在 2025 年 12 月把 Skill 规范作为开放标准发布，目前已被 33+ 个 Agent 产品采纳（Claude Code、Codex、GitHub Copilot、Cursor、Gemini CLI…）。所以你现在写的 SKILL.md，换个 Agent 也能用。这是本课最值得花时间的一章。

三级加载：为什么 100 个技能不炸上下文

级别加载什么成本时机
L0skills_list() — 所有技能的 name + description≈3000 tokens，全场固定会话开始
L1skill_view(name) — 完整的 SKILL.md 正文几百到几千 tokens我判断需要它时
L2skill_view(name, "references/x.md") — 单个参考文件按需正文里指路时

08把 Agent 当操作系统用

同一个模型，编排方式不同，产出差 10 倍。这一章讲"什么活该用什么姿势派"。

到这一步你已经会配了。但配好之后最常见的浪费是：所有活都用"直接干"这一种姿势——你说需求，我埋头写，写完你发现方向错了，重来。

五种编排姿势

姿势解决什么问题什么时候用成本
直接干—小改动、路径唯一的活最低
计划模式
plan-mode		方向跑偏多文件改动、架构选择、你也没想清楚低（多一轮）
对抗提问
grill-me		方案本身是错的动手前、重大决策前低，回报最高
分身
delegate_task		上下文被污染 / 要并行调研、批量处理、互不依赖的多条线中（子代理会烧 token）
定时
cron		需要周期性/到点提醒监控、日报、定时检查低（无人值守）

① 计划模式：先看图纸再施工

你装了 plan-mode 插件，它让"先出计划、等你批准"变成强制流程，而不是靠我自觉。

用法
# 方式一：斜杠命令（内置 plan skill，任何环境都能用）
/plan 给论文库加一个按 tag 检索的命令行子命令

# 方式二：插件强制模式（会拦住我，不批准不许改文件）
/planmode

# 方式三：直接说人话
先别动手。给我一个方案：要改哪几个文件、每个文件改什么、有什么风险。我点头你再动。
为什么这一步性价比最高

改 5 个文件之后发现方向错了，损失的是 5 个文件的返工 + 你判断的时间。先看 10 行方案只要 30 秒。方案比代码便宜一个数量级。

② 对抗提问：让 Agent 反过来审你

grill-me 这个技能会让我扮演质疑者，对着你的计划连续发问，直到露出漏洞。初学者最缺的不是执行力，是"有人问你为什么这么做"。

用法
/grill-me 我打算用 SQLite 存论文元数据，笔记存 Markdown 文件

# 或者更直接的问法
在这个方案动手前，找三个会让它失败的原因。不要安慰我。

③ TDD + 审查：给"写完了"加一道闸

标准三步
/test-driven-development 实现 parse_arxiv_id()，输入 URL/ID 都要能解析

# 写完之后，提交之前
/requesting-code-review

# 代码变多了、想清理
/simplify-code

TDD 的核心约束是先写一个会失败的测试。它防的不是"写错"，是"写了一堆你以为对的东西，其实没人验证过"。

④ 分身：为什么要"另开一个脑子"

delegate_task 会起一个上下文完全独立的子代理。它的价值不是"并行更快"，而是不污染主对话。

类比：你要查 20 个网页写调研。让主线程去查，20 个网页的全文会全塞进对话，等你回到正事时，上下文已经被垃圾填满（还会更贵、更容易忘事）。派个分身去查，它只带回一张摘要表。
分身最大的坑：它的汇报不可信

子代理说"已完成上传"、"文件已写好"，这是自述，不是事实。所以派活时必须要求它交出可验证的凭据：绝对路径、URL、commit hash。然后我去核对。这条规则对任何 Agent 都成立。

⑤ 定时：无人值守的那部分

典型用途
每天早上 8 点：把 arXiv 上 cs.CL 的新论文标题+摘要摘要成 5 条发给我
每周一：检查 D:\code 下所有仓库有没有未提交的改动，列出来
每小时：盯着某个网页有没有变化，变了才通知我

说人话就行，我会把它变成 cron 任务。注意：定时任务的结果需要投递渠道（桌面通知 / 消息平台），第 9 章会用到。

一套"标准施工流程"（建议直接抄）

从想法到落地
① 我描述目标（用大白话，不用管术语）
② 你回一个方案 + 风险 + 需要我决定的分叉点
③ 我挑一个选项（或说"就按你说的"）
④ 你动手，边做边报关键节点
⑤ 做完给我：改了哪些文件 + 怎么验证 + 跳过了什么
⑥ 复盘：这次的流程值不值得存成 skill？（→ 第 10 章）

把这段直接发给我一次，我会把它当成默认协作方式（也会建议存进 SOUL.md 或 memory）。

10让它越用越懂你

前面九章是"你配它"。这一章是"它自己长"——Hermes 真正区别于其他 Agent 的地方。

闭环长什么样

自进化回路
干一件没干过的事
  → 中途踩坑、绕路、被你纠正
  → 干完了
  → 【关键】问一句："这套流程值得存成 skill 吗？"
  → 存（skill_manage）→ 下次直接复用，不用再教
  → 用了几次发现有问题 → patch 更新它
  → 长期没用的 → curator 自动归档

90% 的人卡在第 4 步。活干完了就关窗口，下次同样的活从头教一遍。这不是记性问题，是习惯问题。

三句话触发沉淀

干完活之后，随手发一句
# 1. 沉淀
把刚才这套流程存成 skill，名字你自己定，description 要含"论文/PDF/精读"这些词。

# 2. 修正（比新写更重要）
刚才第三步走弯路了。把正确做法补进那个 skill 的"坑"里，别重写整个文件。

# 3. 清理
我这个 skills 目录里，哪些是我自己写的、而且从没被用过？列出来。

curator：自动打扫，但只归档不删除

项目行为
触发条件距上次运行 ≥7 天 且 你闲置 ≥2 小时（不是定时任务，是空闲检查）
状态流转active → stale → archived
管谁默认只管你和 Agent 自建的技能；内置技能要显式开 curator.prune_builtins 才管
安全性从不自动删除，最坏是移到 skills\.archive\，可恢复
不管谁Hub 装的技能永远不动

意义：你不必担心"技能越攒越多把上下文撑爆"，但也别指望它替你判断价值——归档的是"没人用"，不是"没用"。

周五下班前，一次发完
做个每周检查：

最后一个元技能：识别"它在糊弄你"

症状真相怎么反击
说"已完成""已修复"工具调用成功 ≠ 任务成功要求给出可验证凭据：路径、命令输出、hash

不是 Hermes 的命令，而是这四件事：① 分层配置（什么放哪）② 预算意识（常驻必须短）③ 渐进披露（长的按需加载）④ 验证习惯（说的不等于做的）。这四条换到 Claude Code、Codex、Cursor 上，一字不改都成立。

11外观层：皮肤、桌宠、状态可见性

这一层不影响能力，但决定你愿不愿意天天打开它。它是最便宜的一次性投入。

先把三样东西分开，否则你会以为它们是一回事：

东西是什么影响范围改法
皮肤 skin一个 YAML 调色板文件CLI + TUI + 桌面应用三端同时hermes skin / hermes config set display.skin
桌面主题插件里注册的主题对象只影响桌面应用写进 desktop-plugin
桌宠 pet会动的精灵图，跟 Agent 状态联动CLI + TUI + 桌面hermes pets

为什么"好看"其实是正经需求

不是审美问题，是信息带宽问题。Agent 干活时你在等，等的时候你不知道它在想、在跑工具、还是卡住了。桌宠和状态条把这三件事变成一眼可见的信号——它不动 = 卡住了，它在跑 = 正在调工具，它变红 = 报错了。

类比：机房里的服务器都长得一样，但运维会给关键机器贴一张会闪的便签。便签不增加算力，但它让你不用登进去就能知道"这台在干活"。桌宠就是那张便签。
但先问一句：值得吗

如果你每天只看两眼 Hermes，桌宠是玩具。如果你是长时间挂着它干活（写代码、跑长任务），状态可见性的收益远大于成本——因为你会停止"每隔两分钟切窗口看一眼"这个习惯。

皮肤：三端一起换

皮肤是语义化的：一个键管一类元素。所以你不用记"标题用第几个颜色"，只要知道"工具调用的圆点叫 ui_tool"。

你看到的东西对应的键
整个背景background
工具调用标记（那个 ●）、转圈ui_tool（未设则跟随 ui_accent）
思考/推理文字ui_thinking
强调色：标题、链接、箭头ui_accent / banner_accent
正文、你发的消息ui_text / ui_label
次要文字、树状连接线banner_dim
边框、分隔线ui_border / banner_border
成功 / 警告 / 报错ui_ok / ui_warn / ui_error
代码高亮（字符串/数字/关键字/注释）syntax_string / syntax_number / syntax_keyword / syntax_comment
bash · 换皮肤的全部命令
# 看有哪些皮肤
hermes skin list

# 切换（会让 CLi / TUI / 桌面 在一秒内一起重绘）
hermes skin use <名字>
hermes config set display.skin <名字>

# 只改当前皮肤里的某一个颜色（不会丢背景、不会丢其它配色）
hermes skin set ui_tool "#00FFFF"
hermes skin set background "#08201f"
三个必踩的坑

1. 想微调一个颜色，不要去 fork default。从 default 抄一份新皮肤，会顺手丢掉当前调色板和 background，结果是背景被打回终端默认（通常是纯黑）。用 hermes skin set 原地改。

2. 不要手改 config.yaml。一个缩进错误能让整个配置失效（连 / 都起不来）。永远走 hermes config set。

3. 皮肤名不能撞内置。mono / slate / cyberpunk / nous / midnight / ember 这几个名字，你写的同名文件在桌面端盖不掉内置皮肤。换个名字。

桌宠：装一个，然后忘了它

桌宠来自公开画廊 petdex，装到 <HERMES_HOME>\pets\。它会跟着 Agent 的状态切换动作：空闲 / 跑工具 / 思考 / 报错 / 完成。

bash · 桌宠全流程
# 1. 逛画廊（可带关键词过滤）
hermes pets list
hermes pets list cat

# 2. 装并设为当前
hermes pets install <slug> --select

# 3. 在终端里预览效果（Ctrl+C 停）
hermes pets show

# 4. 大小不合适就调（0.1 ~ 3.0）
hermes pets scale 0.5

# 5. 体检：确认装好、选中、启用
hermes pets doctor

# 6. 不想要了
hermes pets off          # 只关掉，不删
hermes pets remove <slug> # 真删
配置项（display.pet）作用
enabled总开关
slug当前用哪只；空 = 用第一只已安装的
render_modeauto 自动检测 / kitty / sixel / unicode / off
scale尺寸，默认 0.33
unicode_colsUnicode 降级渲染时的宽度
桌宠不显示的四个原因（按概率排）

1. 装了但没 select——必须安装 且 选中 且 enabled: true。

2. 在管道/重定向里跑（没有 TTY）——这是设计如此，不是 bug。

3. 终端不支持图形协议——会自动降到 Unicode 半块渲染，看起来像"像素画"，那不是坏了。

4. 你用 petdex 的 npm CLI 装到了 ~/.codex/pets——那是给别的工具用的，Hermes 只认自己的 pets\ 目录。用 hermes pets install。

12工作台：桌面插件、管理台、多开

把 Hermes 从"聊天窗"变成"操作台"。这一章决定你是一个人在用，还是有一套系统在用。

聊天窗的问题是一切都要问一遍：现在几个任务在跑？哪个仓库有未提交改动？今天花了多少 token？——每次问一遍，就是一次往返。

工作台是把这些问题变成常驻可见的。有四种做法，成本从低到高：

做法给你什么成本什么时候值得
管理台 hermes dashboard网页版配置/密钥/会话管理一条命令你要改配置、看历史会话
多开 Profile几套互不干扰的 Hermes（配置/技能/记忆各自独立）一条命令工作与学习分开、或要不同模型
桌面插件应用里的常驻面板 / 状态栏 / ⌘K 命令 / 主题一个 JS 文件你每天都会看的那一个数字
TUI 小组件终端 TUI 里停靠的小面板一个 .mjs 文件你主要用终端而不是桌面应用

① 管理台：一条命令就有

bash
hermes dashboard            # 起服务并打开浏览器
hermes dashboard --status   # 看它在不在跑
hermes dashboard --stop     # 关掉

里面有消息渠道、MCP 目录、webhook、记忆、以及一个内嵌的聊天窗口。改配置比手改 YAML 安全。

② 多开 Profile：给每件事一个独立的脑子

一个 profile = 一套独立的 config.yaml + skills/ + 记忆 + 会话库。它们互不污染。

bash
hermes profile list                 # 现在有哪些
hermes profile create research      # 新建一个叫 research 的
hermes -p research                  # 用 research 这个开聊
hermes profile show research        # 看它长什么样
profiles 最容易被忽略的用途

不是"多个账号"，而是隔离上下文。你的编程 profile 里塞满了几百条调试记忆，切到论文 profile 时，那些东西本来就不该出现——它们既占预算又干扰判断。分开之后，每个 profile 都很"干净"。

③ 桌面插件：一个 JS 文件，不用编译

放到 <HERMES_HOME>\desktop-plugins\<id>\plugin.js，保存即热重载，不需要重启、不需要打包。可以注册：状态栏小片、可拖拽面板、⌘K 命令、快捷键、整页视图、甚至主题。

desktop-plugins\hello\plugin.js · 最小可用
import { jsx } from 'react/jsx-runtime'

export default {
  id: 'hello',
  name: 'Hello 状态条',
  register(ctx) {
    ctx.register({
      id: 'hello-chip',
      area: 'statusBar.right',
      order: 10,
      render: () => jsx('span', {
        style: { fontSize: 11, color: 'var(--ui-text-secondary)' },
        children: '在跑',
      }),
    })
  },
}
你想做的area
状态栏右边一个小片'statusBar.right'
一个可拖拽的面板'panes'（配 placement 或 dock）
⌘K 里的一个命令PALETTE_AREA
一个整页（带侧栏入口）ROUTES_AREA + SIDEBAR_NAV_AREA
聊天里的自定义指令（::xxx{}）TRANSCRIPT_DIRECTIVE_AREA
桌面插件的四个硬坑

1. 写 JSX 语法会直接解析失败。文件不编译，必须用 jsx('div', {...}) 函数调用。

2. 不能硬编码颜色。面板本来就铺在应用的背景上，写 #000 在亮色主题下就是一块黑砖。用 var(--ui-accent) 这类主题变量。

3. 只导入三样东西：@hermes/plugin-sdk、react、react/jsx-runtime。别的模块名解析不了。

4. 忘了 import 的组件会报 ReferenceError。报错会以 toast 形式弹出来，指名道姓告诉你哪个名字没定义——照着改就行。

装好后去 设置 → Plugins 里能开/关（关掉后重启也保持关闭）。如果没出现，⌘K 里搜 Reload desktop plugins 手动重载一次。

④ TUI 小组件：给纯终端用户

如果你主要用 hermes --tui，小组件放在 <HERMES_HOME>\tui-widgets\ 下（注意：它不是一条 CLI 命令，没有 hermes tui-widgets，只是目录约定 + TUI 里停靠）。适合时钟、ticker、监控面板这类"一直在那儿"的东西。

判断标准：什么才值得做成面板

三问
1. 这个信息我每天会看超过 3 次？        —— 否则别做
2. 每次获取要花超过 30 秒（问一遍+等回答）？—— 才值得
3. 它出错时我会不会不知道？              —— 会，才值得（监控类优先级最高）

三条里满足两条才动手。绝大多数人第一条就过不了——那就别做，直接问我就行。

B30 天路线
